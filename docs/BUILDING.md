# Building, testing and relinking

## Pinned asset-free container build

The reference toolchain is Emscripten **6.0.5**. A Docker recipe avoids depending on a developer's SDK installation. Run from this repository's root:

```sh
IMAGE=emscripten/emsdk:6.0.5@sha256:76a44fff907397784decc435115d07fcb9587a4f1504977f39f3745e538e3a1e
docker pull "$IMAGE"
docker run --rm --network none \
  --user "$(id -u):$(id -g)" -e HOME=/tmp \
  --mount "type=bind,source=$PWD,target=/src" -w /src "$IMAGE" \
  bash -c 'set -e; export EMSDK=/emsdk; source "$EMSDK/emsdk_env.sh"; ./web/build.sh; ./tools/check.sh'
```

Only the source checkout is mounted; no purchaser files are required. Pulling the image uses the network; compilation/tests run with container networking disabled. `/tmp` here is disposable container-local storage. This is a portable build recipe, not a sandbox for deliberately hostile source code.

The outputs are `web/dist/i76web.mjs`, `web/dist/i76web.wasm` and `web/dist/stamp.json`. The build identifies a Git checkout by its short commit ID; an archive without Git metadata reports `unknown`. This is build identification, not a claim of byte-for-byte reproducibility across toolchains or commit IDs.

The `web/` shell also needs its checked-in JavaScript and styles. Serve the repository root using the README command. Do not upload a developer working directory or publish build outputs accidentally. The hosted build is produced only by `tools/build_site.sh <new-output-dir>`, which refuses a dirty checkout and copies an explicit allowlist plus the commit's source tarball.

## Test scope

`tools/check.sh` fails if its source-inventory or asset-free tests fail. The tests use generated bytes and no purchased content. They cover selected routing, shell-art/music logic, engagement decisions, and compiled-engine initialization/rejection with no archives present. They do **not** establish a playable campaign or malformed-input coverage for every format.

`tools/test_lzodec.py` separately tests generated LZO streams with native address/undefined-behavior sanitizers and a system reference library. On Ubuntu 24.04 install `clang libclang-rt-dev liblzo2-2`, then run `CC=clang python3 tools/test_lzodec.py`. The separate compiler-runtime package supplies the sanitizer libraries. Mutations may remain valid compressed streams; the test checks sanitizer failures and output contracts, not that every mutation must be rejected.

`tools/check_owned.sh` runs selected port-Wasm component scenarios only when `NITRO_APP` explicitly names a purchaser-owned Nitro `app/` directory outside the checkout, with a trailing slash. Those inputs never belong in CI, commits, issue attachments or source archives. Optional public renderer/replay tools and their prerequisites are documented in [TESTING.md](TESTING.md). Browser/renderer/original-executable checks are not silently counted as public CI successes.

## Source-export audit versus development checks

`python3 tools/check_source.py` is the strict source-only inventory check. Run it on the final fresh `git archive` extraction **before installing dependencies or building**. It rejects extra files, binary content, source symlinks and generated outputs; it is not a secret scan or copyright audit.

`tools/check.sh` deliberately uses `check_source.py --working-tree`: that mode permits local `node_modules`, Python caches and the three named Wasm outputs, which it does **not** audit. This makes testing an installed developer checkout possible without declaring its dependency/build directory distributable. Never substitute the working-tree mode for the final strict export audit. Keep `PUBLIC_FILES.txt` in sync with intentional source additions/removals and independently review its changes.

## Modify and relink libsmacker

The library is linked from source directly by `web/build.sh`; there is no separately downloaded decoder blob or locked signing step.

1. Keep the exact application source, library source and build recipe matching the binary you are modifying.
2. Make your changes in `third_party/libsmacker/`, retaining its LGPL and copyright notices. Mark your changes when redistributing them.
3. Re-run `web/build.sh` with the pinned SDK, or use the container recipe above. The command compiles the modified `smacker.c` and links it into a new `i76web.wasm` alongside the application.
4. Run the asset-free tests, then test your decoder with your own `.smk` files through the local page. Do not add those movies or captured frames to the repository.
5. Use the newly built loader, Wasm and stamp together; reload the page to avoid stale cached code.

Before distributing a binary, publish its matching complete source and build instructions, preserve applicable toolchain/runtime notices, and link the binary to that source and LGPL text. These instructions enable a source rebuild/relink; they are not a substitute for reading the applicable licence requirements. The hosted build at https://i76-webgpu.netlify.app follows this: each deployment serves its exact source at `/source/`.
